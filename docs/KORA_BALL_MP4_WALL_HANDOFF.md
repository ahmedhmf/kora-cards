# KORA rendered-ball activity → event TV Wall (MP4 integration handoff)

> **Share this file with the chat implementing the separate rendered-ball
> activity.** This is the integration contract for uploading rendered-ball
> MP4 clips so they rotate alongside PNG player cards at
> `https://kora-cards.vercel.app/wall`. Changes are developed on
> `feat/kora-wall-ball-mp4` and are **not live until the SQL, function and
> frontend are deployed**.

## What the TV Wall will do

- Same existing **6 columns × 2 rows** (12 portrait slots), same KORA/SFL/REFUEL
  header, wall access code and Instagram QR.
- A slot can show either a player's **PNG card** (with that card's existing
  seven-day download QR) or a **rendered-ball MP4 clip** (no QR).
- Clips **autoplay muted, loop and play inline** using HTML5 `<video>`.
  The whole video is contained in the slot, without stretching or cropping.
- The screen refreshes the feed every 30 seconds, flips a tile every 3.5
  seconds when there are more than 12 items, and holds a visible video for
  **at least 15 seconds** before replacing that tile. For best presentation,
  export a **short 6–12 second seamless loop**.
- Media is removed from the wall **60 minutes after its successful upload**,
  even if the screen loses network connection. Removal from the wall does not
  automatically delete the private stored MP4.
- All player-card upload, player consent and seven-day QR-download behavior
  stays unchanged. **Do not upload MP4s through `kora-card-upload`**:
  that existing endpoint only accepts player-card PNGs.

## Supabase schema and storage — run once by the operator

1. In the **same Supabase project used by KORA Cards**, run
   `supabase/kora-wall-ball-videos.sql` via Supabase SQL Editor.
   This creates a **private** Storage bucket called `kora-wall-media` and
   a private metadata table `public.kora_wall_ball_videos`.
2. The database table has:
   - `id`: UUID primary key, generated by DB.
   - `storage_path`: unique **bucket-relative** MP4 object path.
   - `uploaded_at`: server timestamp; wall 60-minute countdown starts here.
   - `approved`: boolean, defaults **false**.
   - `event_screen_consent`: boolean, defaults **false**.
3. Anonymous/authenticated client roles have **no table access**. The
   `service_role` handles uploads and table changes. Storage has no public
   object policy; the wall feed signs short-lived playback URLs.
4. The wall feed additionally requires the existing
   `KORA_WALL_ACCESS_KEY`, `KORA_ALLOWED_ORIGINS`, `SUPABASE_URL`
   and Supabase server-side secret/service-role credential. Never place
   those secrets in a mobile/browser bundle or commit them to GitHub.

## What the rendered-ball activity's implementer must build

**Use a trusted server-side upload endpoint** (or a protected Supabase Edge
Function) with appropriate authentication, authorization and rate limits.
Do **not** let arbitrary visitors write directly to the bucket or set
`approved=true` from client input.

1. Obtain a fully rendered MP4 from the ball activity.
   **Recommended encoding:** MP4 container, H.264/AVC video,
   `yuv420p`, no required audio, portrait aspect ratio (e.g. 720×1280),
   24–30 fps, 6–12 seconds and optimized for streaming (faststart). Avoid
   HEVC-only files; many smart-TV browsers won't play them.
2. Obtain a **separate, explicit opt-in** from the participant for
   showing this rendered ball on the event TV. Display consent must not be
   silently inferred from the player-card form. If this is an
   operator-created promotional ball video without an identifiable person,
   record an equivalent authorization/approval decision. If consent is
   refused, do not publish that clip to the wall.
3. Validate on the trusted server that the bytes are a real MP4 (not just
   a renamed file), the MIME type is `video/mp4`, the size is within the
   bucket's **100 MiB** limit, and codec/duration/resolution meet your
   product limits. For reliability, transcode rather than trusting client
   metadata. Apply upload quotas and prevent path traversal.
4. Generate an unpredictable UUID. Upload to the **private** Supabase
   Storage bucket `kora-wall-media`, using a bucket-relative path:
   `balls/<event-slug>/<uuid>.mp4`
   where the event slug uses letters, numbers, `_` or `-`.
   Send `contentType: 'video/mp4'` and use `upsert: false`.
5. **After Storage confirms success**, insert a metadata row into
   `public.kora_wall_ball_videos` via the trusted server:
   `storage_path` = the exact object path,
   `uploaded_at` = server's current timestamp (default from database),
   `event_screen_consent=true` **only when explicitly authorized**,
   and `approved=true` **only after moderation/approval**.
   You may create the row as both flags false and turn them on only after
   approval. Both must be true for the wall to show it.
6. On metadata insertion failure, remove the orphaned Storage object or
   send it to an operator cleanup queue. Duplicate paths are rejected.
   Never expose the service-role key, raw database row details, or any
   participant contact data to the public PWA.
7. A clip appears on the wall automatically on the next refresh (~30s)
   **if** it is fresh, consented, approved and the wall is connected.
   No need to edit the card uploader or manually send a URL to the TV.

### Trusted server pseudocode (Supabase JS)

```ts
// RUN SERVER-SIDE ONLY. `supabaseAdmin` must use a secret credential.
// `mp4Bytes` must already be authenticated, validated and authorized.
// `consentGranted` and `operatorApproved` must be checked server-side.
if (!consentGranted) throw new Error('Event display consent required');
if (!operatorApproved) throw new Error('Approval required');
const path = `balls/${safeEventSlug}/${crypto.randomUUID()}.mp4`;
const { error: uploadError } = await supabaseAdmin.storage
  .from('kora-wall-media')
  .upload(path, mp4Bytes, { contentType: 'video/mp4', upsert: false });
if (uploadError) throw uploadError;
const { error: rowError } = await supabaseAdmin
  .from('kora_wall_ball_videos')
  .insert({
    storage_path: path,
    event_screen_consent: true,
    approved: true
  }); // omit uploaded_at: database defaults to the upload registration time
if (rowError) {
  await supabaseAdmin.storage.from('kora-wall-media').remove([path]);
  throw rowError;
}
```

**Note:** The metadata field `storage_path` is **not** a public URL and
does not contain the bucket prefix. No manual signed URL generation is
needed from the uploader.

## Feed response contract (implemented by the wall branch)

The protected GET `/functions/v1/kora-wall-feed?offset=0` returns:

```json
{
  "cards": [
    {
      "path": "<private PNG object path>",
      "url": "<10-minute signed PNG URL>",
      "qrUrl": "<seven-day token download URL>",
      "uploadedAt": "<ISO timestamp>"
    }
  ],
  "videos": [
    {
      "path": "balls/event-1/<uuid>.mp4",
      "url": "<10-minute signed MP4 URL>",
      "uploadedAt": "<ISO timestamp>"
    }
  ],
  "nextOffset": null
}
```

Both collections are paginated in batches of 80 with the same offset. The
frontend normalizes them into a shared newest-first set and enforces the
one-hour cutoff. Only the trusted wall feed sees and signs private MP4 paths.
The `kora-wall-download` function still handles player **PNGs only**;
**no download QR is created for ball MP4s** in this version.

   (project ref in KORA docs: `lijrppvvwomrvoxtrcaj`).

5. The ball-activity team deploys its own **trusted upload endpoint** with
   secrets managed server-side; that endpoint is **not included** in the
   wall branch.

## Acceptance test

- Upload a consenting, approved 6–12 second H.264 MP4 via the trusted
  uploader. Insert one `kora_wall_ball_videos` row with the exact path.
- With a working event access code, open `/wall`. Within ~30 seconds the
  video should appear and loop muted in a tile next to player cards.
- Confirm player cards still show scannable QR codes, with the existing
  seven-day links. Videos must **not** get a card download QR.
- Confirm a clip with `approved=false` or
  `event_screen_consent=false` is not shown.
- Confirm a video older than 60 minutes disappears even with no network
  connection; no unintended personal metadata is exposed.
- Test on the **real TV browser**: it must support H.264 MP4, muted autoplay,
  playback of private signed URLs and multiple video tiles.
- Test Vercel/Angular production build and function logs before the event.
  If the TV browser cannot decode multiple videos simultaneously, reduce
  concurrent videos or make a dedicated video tile mode.

## Scope and non-goals

This branch adds **wall playback**, a secure table/bucket contract and
documentation. It does **not** implement the rendered-ball capture/editor,
transcoding, authenticated upload server or moderation UI. The other chat
should build those pieces from this file and coordinate schema deployment.
No passcode or secret key should be pasted into chat.
